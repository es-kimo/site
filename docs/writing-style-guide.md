# 기술 블로그 글 작성 스타일 가이드: 지양해야 할 AI 문체

이 문서는 사람이 직접 작성한 것처럼 자연스럽고 높은 가독성을 유지하기 위해, 기술 블로그 포스트 작성 시 **반드시 지양해야 할 AI 특유의 문체와 안티패턴** 및 **권장하는 작성 원칙**을 정리한 가이드라인입니다.

---

## 1. 지양해야 할 AI 특유의 어조와 문장 구조

### ❌ 1) 가르치려는 훈계조 및 비장한 수사 ("~한 진짜 이유는 ~하기 위함이었습니다")
"React 팀이 이 규칙을 둔 진짜 이유는 ~하기 위함이었습니다"처럼 마치 비하인드 스토리를 훈계하듯 가르치는 문체는 AI 특유의 상투적 서술입니다. 담백하게 기술적 인과관계와 장점을 서술합니다.

- ❌ **지양 예시**:
  > React가 "최상위에서만 호출해야 한다"는 단순한 규칙을 둔 진짜 이유는, 개발자가 Key 충돌을 신경 쓰지 않고 커스텀 훅을 자유롭게 조합할 수 있도록 만들기 위함이었습니다.
- ⭕ **권장 예시**:
  > 이러한 호출 순서 규칙 덕분에, 개발자는 Key 충돌이나 전달 과정을 신경 쓰지 않고 커스텀 훅을 자유롭게 중첩하고 조합할 수 있습니다.

---

### ❌ 2) 모호하거나 철학적인 제목 / 자극적인 유튜브식 제목 지양
글과 소제목은 독자가 무엇을 배울 수 있는지 직관적이고 차분하게 전달해야 합니다.

| 지양하는 제목 (모호함/자극적/어색함) | 권장하는 제목 (직관적·구체적) |
| :--- | :--- |
| **다시 실행되는 범위는 누가 정하는가** | **React 리렌더링 범위는 어떻게 결정될까** |
| **훅의 정체, 이름이 아닌 호출 순서로 매핑되는 슬롯** | **훅의 상태 저장 방식: 호출 순서 기반 슬롯** |
| **조건부 호출이 슬롯 순서를 어긋나게 만드는 과정** | **훅의 호출 순서가 바뀌면 발생하는 문제** |
| **훅에 고유 식별자(Key)를 넘기면 안 될까** | **Key를 직접 넘기는 방식의 한계** |

---

### ❌ 3) 뻔한 유도문 및 인위적 반전 ("처음에는 ~하지만, 알고 나면...")
독자에게 어설프게 공감대를 형성하려 하거나("처음에는 왜 이렇게 제약이 많을까 하고 넘어가기 쉽습니다"), 뻔한 반전을 유도하지 않고 본론으로 바로 들어갑니다.

- ❌ **지양 예시**:
  > 처음에는 왜 이렇게 제약이 많을까 하고 넘어가기 쉽습니다. 하지만 React 내부에서 훅이 실제로 어떻게 상태를 기억하는지를 알고 나면, 왜 이 규칙이 지켜져야 하는지 자연스럽게 이해할 수 있습니다.
- ⭕ **권장 예시**:
  > React는 왜 훅을 반드시 컴포넌트 최상단에서 일정한 순서로만 호출하도록 제한할까요? 이유를 알기 위해서는 React가 훅의 상태를 메모리에 저장하고 꺼내오는 방식을 살펴볼 필요가 있습니다.

---

### ❌ 4) 기계적인 '정리하며 / 요약' 섹션 의무화 지양
모든 글의 끝에 관성적으로 '## 정리하며'나 기계적인 3줄 요약 섹션을 붙이는 것은 AI 글의 대표적인 상투적 패턴입니다.
- 실무 적용 패턴, 구체적 해결책, 또는 기술적 시사점을 담은 본문 마지막 섹션에서 글을 자연스럽게 완결 짓습니다.
- 굳이 결론 섹션이 필요하지 않은 글에 억지 요약이나 교훈조 Callout을 덧붙이지 않습니다.

---

### ❌ 5) 인위적인 대구/이분법 템플릿 ("절반만 맞습니다...", "A는 설명하지만 B는...")
- ❌ **지양 예시**:
  > 이 말은 절반만 맞습니다. 다시 실행되는 범위가 어디서 시작하는지(시작점)는 설명하지만, 그 범위가 어디서 끝나는지(끝점)에 대해서는 답을 주지 못하기 때문입니다.
- ⭕ **권장 예시**:
  > 대부분의 경우 부모가 리렌더링되면 자식 컴포넌트들도 함께 호출됩니다. 하지만 React 내부를 들여다보면 특정 조건을 만족할 때 하위 트리의 실행을 건너뛰는 Bailout 메커니즘이 존재합니다.

---

### ❌ 6) 과장된 감정 수식어 및 자극적인 어휘 지양
기술 문서에서 불필요하게 감정적이거나 과장된 단어('가차 없이', '놀랍게도', '대참사', '거의 공짜', '단 한 줄도')를 쓰지 않습니다.

| 지양하는 어휘/표현 | 권장하는 정제된 표현 |
| :--- | :--- |
| **가차 없이 빨간 줄을 긋고 에러를 띄웁니다** | **규칙에 의해 다음과 같은 에러가 발생합니다** |
| **놀랍게도 React는 이름을 알지 못합니다** | **자바스크립트 언어 특성상, 로컬 변수명은 React 런타임에 전달되지 않습니다** |
| **3가지 사건** | **3단계 과정** / **3가지 동작** |
| **거의 공짜 (비트 연산 1회)** | **별도의 함수 호출 없이 상태 표시만 확인** |
| **단 한 줄도 화면에 반영하지 않을 수 있습니다** | **실제 DOM은 변경되지 않습니다** |

## 2. 근거와 출처 주석(Footnote) 필수 원칙

"React 팀에서도 이 방식을 검토했습니다"나 "내부적으로 다음과 같이 구현되어 있습니다"와 같이 코어 팀의 의사결정 배경이나 엔진 내부 원리를 설명할 때는 **반드시 공식 문서, RFC, 코어 개발자의 글 등의 출처 주석(`<Footnote>`, `<FootnoteRef>`)을 명시**해야 합니다.

---

## 3. 기술적 대안(Trade-off) 서술 원칙: 줄글 나열 대신 코드 스니펫과 비교표 활용

대안의 한계를 단순 줄글 번호 매기기로 나열하면 독자가 문제를 직관적으로 체감하기 어렵고 가독성이 급격히 떨어집니다.

- **가상 코드 스니펫 제공**: 만약 그 대안(예: Key 기반 훅)을 실제로 썼을 때 어떤 코드 형태가 되고 어디서 충돌이 나는지 짧은 예시 코드로 직접 보여줍니다.
- **핵심 비교 테이블 활용**: 기존 방식과 대안의 차이점(조합성, 코드 간결성, 런타임 성능 등)을 표로 정리하여 한눈에 스캔할 수 있도록 합니다.

## 4. 문장 부호 및 기호 규칙

### ❌ 영문식 대시(`—`, em-dash) 남발 금지
- **개선 방법**: 괄호 `(...)`나 쉼표(`,`)를 활용하거나 부제 형식으로 자연스럽게 풉니다.

### ❌ 문장 끝 콜론(`:`) 남발 금지
- **개선 방법**: 마침표(`.`)로 깔끔하게 끝맺거나 `~는 다음과 같습니다.` 형태로 이어줍니다.

### ⭕ (적극 권장) 학습 흐름을 잡아주는 넘버링 소제목 (`개념 1:`, `1단계:`)
- **이유**: 긴 기술 글에서 단계별 핵심을 짚어주는 **`개념 1: ...`**, **`1단계: ...`** 형태의 소제목은 구조적 전달력이 뛰어납니다.

### ❌ 굵은 글씨(`**`) 및 인위적인 따옴표(`"..."`) 남발 금지
- **개선 방법**: 문단당 최대 1개 수준으로 절제하고, 닫는 `**` 바로 뒤에 괄호나 조사가 붙어 렌더링이 깨지지 않도록 평문으로 작성합니다.

## 5. Mermaid 다이어그램 레이아웃 규칙

### ⭕ 세로 배치(Top-Down) 기본 원칙
- **작성 방법**:
  - `flowchart TD`를 기본 방향으로 사용합니다.
  - 두 개 이상의 `subgraph`를 비교할 때는 서브그래프 사이에 `Sub1 ~~~ Sub2` (투명 연결선) 또는 `Sub1 --> Sub2` (단계 전환선)를 추가하여 **위아래(세로)로 스택 배치**되도록 구성합니다.

| **100% 안전할까요? / 완벽하게 보장합니다** | **안정적으로 동작합니다 / 예측 가능하게 처리됩니다** |
