# GitHub Pages에서 Enforce HTTPS를 켜면 무슨 일이 일어날까

<AIAssisted />

GitHub Pages에 custom domain을 연결하고 나면 설정 화면에 `Enforce HTTPS`라는 체크박스가 나타납니다. 이름만 보면 이 버튼이 사이트를 암호화해 주는 것처럼 보입니다.

그런데 이상한 점이 있습니다. 도메인을 구입한 곳에서는 `A`나 `CNAME` 레코드만 설정했을 뿐이고, 인증서를 구매하거나 웹 서버에 설치한 적은 없습니다. 그런데 체크박스 하나를 켜면 `http://example.com`이 `https://example.com`으로 바뀌고, 브라우저에는 자물쇠까지 표시됩니다.

이 버튼은 정확히 무엇을 바꾸는 걸까요?

결론부터 말하면 `Enforce HTTPS`는 DNS 설정을 바꾸거나 그 순간 새로 암호화를 만드는 기능이 아닙니다. GitHub가 미리 준비한 HTTPS endpoint로 HTTP 요청을 보내지 않도록 강제하는 **redirect 정책**에 가깝습니다.

이 과정을 이해하려면 브라우저가 웹페이지를 받아오기까지의 일을 한 덩어리로 보지 않고, 다음 네 단계로 나눠 보는 것이 좋습니다.

```text
DNS → TCP → TLS → HTTP
```

## DNS는 주소만 찾습니다

우선 `example.com`의 DNS를 다음과 같이 설정했다고 가정해 보겠습니다.

```text
example.com.  A  185.199.108.153
example.com.  A  185.199.109.153
example.com.  A  185.199.110.153
example.com.  A  185.199.111.153
```

이 레코드가 말하는 것은 단순합니다.

> `example.com`이라는 이름은 이 IP 주소들에서 찾을 수 있습니다.

여기에는 80번 포트를 쓸지, 443번 포트를 쓸지, 통신을 암호화할지에 대한 결정이 들어 있지 않습니다. 일반적인 GitHub Pages의 `A` 또는 `CNAME` 구성에서 DNS가 하는 일은 도메인 이름을 GitHub 인프라까지 안내하는 것입니다.<Footnote id="1">1</Footnote>

따라서 아래 두 URL은 같은 도메인을 조회합니다.

```text
http://example.com
https://example.com
```

둘의 차이를 만드는 것은 도메인 앞의 scheme입니다. 브라우저는 `http`를 보면 기본적으로 80번 포트에, `https`를 보면 443번 포트에 연결합니다. DNS 조회가 끝난 다음 단계에서 갈림길이 생기는 셈입니다.

<Callout>
현대 DNS에는 HTTPS 연결 정보를 전달할 수 있는 `HTTPS` 레코드도 있습니다. 다만 GitHub Pages에서 흔히 설정하는 `A`, `AAAA`, `CNAME` 레코드 자체가 HTTP와 HTTPS 중 하나를 선택하는 것은 아닙니다.
</Callout>

## HTTP로 접속하면 먼저 평문 요청이 도착합니다

사용자가 주소창에 `http://example.com/notes`를 입력했다고 해보겠습니다. 브라우저는 DNS에서 얻은 IP의 80번 포트로 TCP 연결을 맺고 HTTP 요청을 보냅니다.

```http
GET /notes HTTP/1.1
Host: example.com
```

GitHub는 `Host` 헤더를 보고 이 요청이 어느 Pages 사이트를 향하는지 구분할 수 있습니다. 이때 해당 사이트에 `Enforce HTTPS`가 켜져 있다면 HTML을 응답하는 대신 HTTPS URL로 이동하라는 응답을 보냅니다. GitHub 문서 역시 이 설정을 켜면 모든 HTTP 요청이 HTTPS로 투명하게 redirect된다고 설명합니다.<Footnote id="2">2</Footnote>

개념적으로는 다음과 같은 응답입니다.

```http
HTTP/1.1 301 Moved Permanently
Location: https://example.com/notes
```

redirect는 서버가 브라우저를 다른 연결로 순간 이동시키는 기능이 아닙니다. 브라우저가 응답의 `Location`을 읽고, 이번에는 `https://example.com/notes`로 **새 요청을 시작**합니다.

```text
브라우저                 GitHub Pages
   │                          │
   │── HTTP 요청 (:80) ──────→│
   │←─ HTTPS로 redirect ──────│
   │                          │
   │── HTTPS 연결 (:443) ────→│
```

여기까지가 `Enforce HTTPS`의 주된 역할입니다. 80번 포트로 들어온 요청에 콘텐츠를 그대로 내주지 않고, 443번 포트를 사용하는 URL로 다시 접속하게 합니다.

하지만 redirect만으로 HTTPS가 완성되지는 않습니다. 브라우저가 443번 포트에 도착했을 때 실제로 안전한 연결을 맺을 수 있어야 합니다.

## HTTP 요청보다 TLS handshake가 먼저입니다

브라우저가 `https://example.com`에 접속할 때는 곧바로 `GET /`을 보내지 않습니다. 먼저 GitHub 서버와 TLS handshake를 진행합니다.

```text
브라우저                              GitHub
   │                                    │
   │──── TCP 연결 (:443) ──────────────→│
   │──── TLS ClientHello ──────────────→│
   │←─── ServerHello + Certificate ─────│
   │                                    │
   │       암호화된 연결 수립             │
   │──── 암호화된 HTTP 요청 ────────────→│
```

이 과정에서 GitHub는 `example.com`에 유효한 TLS 인증서를 제시해야 합니다. 브라우저는 적어도 다음 내용을 확인합니다.

- 인증서의 도메인에 `example.com`이 포함되어 있는가
- 신뢰할 수 있는 인증 기관이 인증서에 서명했는가
- 인증서가 유효 기간 안에 있는가
- handshake 과정에서 인증서에 대응하는 개인 키를 가진 서버임이 확인되는가

검증에 성공하고 암호화에 사용할 키가 합의된 뒤에야 HTTP 요청과 응답이 TLS 안에서 오갑니다. URL에 HTTPS를 썼다는 사실만으로 통신이 안전해지는 것이 아니라, 이 handshake가 성공해야 비로소 HTTPS 연결이 성립합니다.

## 인증서는 GitHub가 준비합니다

그렇다면 사용자가 구매하지도 않은 `example.com` 인증서는 어디서 생겼을까요?

GitHub Pages는 올바르게 설정된 custom domain에 대해 인증서 발급과 설치를 자동으로 처리합니다. 현재 GitHub 문서에 따르면 custom domain을 저장하면 자동 DNS 검사가 시작되고, 검사가 성공하면 Let's Encrypt에 TLS 인증서를 요청하는 작업이 대기열에 들어갑니다. 유효한 인증서를 받으면 GitHub가 Pages의 TLS termination 서버에 인증서를 배포합니다.<Footnote id="3">3</Footnote>

흐름을 단순화하면 다음과 같습니다.

```text
Custom domain 등록
        │
        ▼
DNS가 GitHub Pages를 가리키는지 검사
        │
        ▼
Let's Encrypt에 인증서 요청
        │
        ▼
GitHub의 TLS termination 서버에 배포
        │
        ▼
HTTPS 사용 가능
```

즉 GitHub Pages에서 HTTPS가 동작하려면 서로 다른 두 준비가 필요합니다.

1. GitHub가 해당 도메인에 유효한 인증서를 가지고 있어야 합니다.
2. HTTP 요청을 HTTPS로 보낼지 결정하는 정책이 켜져 있어야 합니다.

첫 번째는 HTTPS 연결 자체를 가능하게 만들고, 두 번째가 바로 `Enforce HTTPS`입니다. 체크박스가 인증서를 만드는 버튼이라기보다 **준비된 HTTPS 연결만 사용하도록 강제하는 버튼**이라고 보는 편이 정확합니다.

인증서 준비에는 시간이 걸릴 수 있습니다. GitHub는 custom domain을 설정한 뒤 HTTPS를 사용할 수 있기까지 최대 한 시간이 걸릴 수 있다고 안내합니다.<Footnote id="4">4</Footnote> 인증서가 아직 준비되지 않았다면 redirect의 목적지는 있어도 브라우저가 그 목적지와 안전하게 연결할 수 없으므로, GitHub는 먼저 DNS와 인증서 상태를 확인합니다.

## 암호화는 저장소가 아니라 GitHub 앞단에서 끝납니다

GitHub 저장소에 들어 있는 `index.html`, CSS, JavaScript 파일은 HTTPS를 알지 못합니다. 정적 파일이 암호화 알고리즘을 구현하거나 인증서를 읽는 것도 아닙니다.

TLS를 처리하는 주체는 GitHub Pages의 앞단 서버입니다.

```text
브라우저
   │
   │ TLS로 암호화된 통신
   ▼
GitHub edge / frontend
   │
   │ TLS termination
   ▼
Pages serving infrastructure
   │
   ▼
정적 파일
```

외부에서 들어온 TLS 연결을 앞단 서버가 받아 복호화하고, 그 뒤의 서비스가 요청을 처리하도록 넘기는 것을 **TLS termination**이라고 부릅니다. 개발자가 인증서를 저장소에 올리지 않아도 되는 이유도 여기에 있습니다. 인증서와 개인 키는 HTML 파일이 아니라 GitHub가 운영하는 서버 계층에 속합니다.

여기서 “termination 뒤의 GitHub 내부 통신도 평문이다”라고까지 단정할 수는 없습니다. 공개 문서로 확인할 수 있는 것은 사용자의 TLS 연결이 Pages의 TLS termination 서버에서 처리된다는 사실입니다. 그 이후 내부 구간을 어떻게 보호하는지는 별개의 구현 문제입니다.

## `www`도 별도의 hostname입니다

`www.example.com`을 다음처럼 연결하는 경우도 원리는 같습니다.

```text
www.example.com.  CNAME  username.github.io.
```

DNS는 CNAME을 따라 GitHub Pages의 IP를 찾습니다. 그러나 TLS handshake에서 브라우저가 요청한 hostname은 여전히 `www.example.com`입니다. 따라서 GitHub가 제시하는 인증서에도 이 이름이 포함되어 있어야 합니다.

```text
DNS가 찾아간 곳: username.github.io가 가리키는 GitHub 서버
인증서가 증명할 이름: www.example.com
```

“결국 같은 GitHub 서버로 가니 `github.io` 인증서면 충분하지 않을까?”라고 생각하기 쉽지만, 브라우저는 접속하려던 hostname과 인증서의 이름을 비교합니다. 목적지 IP가 같다는 사실만으로는 충분하지 않습니다.

그래서 GitHub는 custom domain의 DNS 구성을 검사하고, 해당 hostname에 맞는 인증서를 준비합니다. CAA 레코드를 사용 중이라면 `letsencrypt.org`의 인증서 발급을 허용해야 한다는 제약도 있습니다.<Footnote id="5">5</Footnote>

## HTTPS로 직접 접속하면 체크박스는 할 일이 거의 없습니다

사용자가 처음부터 `https://example.com`을 입력했다면 80번 포트의 HTTP 요청은 발생하지 않습니다. 브라우저는 443번 포트로 연결해 TLS handshake를 하고, 성공하면 암호화된 HTTP 요청을 보냅니다.

이 경로에서 중요한 것은 인증서와 TLS 설정입니다. 이미 HTTPS로 들어온 요청을 다시 HTTPS로 redirect할 필요는 없으므로 `Enforce HTTPS` 정책이 개입할 일도 거의 없습니다.

이 차이를 표로 정리하면 다음과 같습니다.

| 처음 입력한 URL | 첫 연결 | TLS handshake | `Enforce HTTPS`의 역할 |
| --- | --- | --- | --- |
| `http://example.com` | TCP 80 | 없음 | HTTPS URL로 redirect |
| `https://example.com` | TCP 443 | HTTP보다 먼저 수행 | 이미 HTTPS이므로 redirect 불필요 |

물론 한 번 HTTPS로 접속한 브라우저는 HSTS 정책이나 브라우저의 HTTPS 우선 동작에 따라 네트워크에 HTTP 요청을 보내기 전에 URL을 HTTPS로 바꿀 수도 있습니다. 이 경우에는 GitHub의 80번 포트까지 요청이 도달하지 않습니다. 그렇더라도 `Enforce HTTPS`의 서버 측 의미가 달라지는 것은 아닙니다.

## HTTPS가 숨기는 것과 숨기지 않는 것

HTTP에서는 요청과 응답이 평문으로 흐릅니다. 같은 네트워크에서 트래픽을 관찰할 수 있는 공격자는 경로나 응답 본문을 읽고, 중간에서 내용을 바꿀 수도 있습니다.

HTTPS에서는 HTTP 메시지가 TLS 안에 들어갑니다.

```text
외부에서 관찰 가능한 정보
  - 연결 대상 IP
  - 443번 포트 사용
  - 통신 시점과 대략적인 크기
  - 환경에 따라 드러날 수 있는 hostname

TLS가 보호하는 HTTP payload
  - 요청 path와 query string
  - 요청 header와 cookie
  - 요청 body
  - HTML, CSS, JavaScript를 포함한 응답 body
```

HTTPS가 인터넷상의 모든 정보를 감추는 것은 아닙니다. DNS 질의를 암호화하지 않았다면 조회한 도메인이 보일 수 있고, TLS의 SNI도 ECH를 사용하지 않는 환경에서는 hostname을 노출할 수 있습니다. 반면 HTTP 요청의 구체적인 내용은 TLS 연결이 만들어진 뒤 암호화됩니다.

또 하나 주의할 점은 mixed content입니다. 문서 자체를 HTTPS로 받았더라도 이미지나 스크립트를 `http://` URL로 불러오면 브라우저가 이를 차단하거나 페이지의 보안 수준을 떨어뜨릴 수 있습니다. GitHub도 HTTPS를 켠 뒤 모든 asset을 HTTPS로 제공하라고 안내합니다.<Footnote id="6">6</Footnote>

## 네 계층으로 다시 보기

처음의 질문으로 돌아가 보겠습니다. `Enforce HTTPS`를 켰을 때 벌어지는 일을 이해하려면 각 계층의 책임을 섞지 않는 것이 중요합니다.

```text
DNS
"example.com은 어디에 있습니까?"
        ↓
GitHub Pages의 IP 주소

TCP
"그 서버의 어느 endpoint와 연결합니까?"
        ↓
HTTP는 80, HTTPS는 443

TLS
"이 서버가 example.com이 맞으며, 어떻게 암호화합니까?"
        ↓
인증서 검증과 세션 키 합의

HTTP
"어떤 리소스를 요청하고 무엇을 응답합니까?"
        ↓
redirect 또는 실제 HTML
```

DNS는 GitHub까지 가는 길을 알려줍니다. GitHub는 custom domain을 확인해 인증서를 발급받고, 앞단 서버에서 TLS 연결을 처리합니다. 그리고 `Enforce HTTPS`는 80번 포트로 들어온 HTTP 요청에 실제 페이지 대신 HTTPS 주소를 돌려줍니다.

따라서 이 설정을 한 문장으로 요약하면 다음과 같습니다.

<Callout>
GitHub Pages는 custom domain의 TLS 인증서를 자동으로 관리하고 443번 포트에서 TLS를 terminate합니다. `Enforce HTTPS`는 80번 포트로 들어온 HTTP 요청을 그 HTTPS endpoint로 redirect하는 정책입니다.
</Callout>

체크박스 하나가 단순해 보이는 이유는 DNS 확인, 인증서 발급, TLS termination 같은 복잡한 일을 GitHub가 대신 맡고 있기 때문입니다. 버튼 뒤에서 새로운 네트워크 원리가 생기는 것은 아닙니다. 이미 분리되어 있던 `DNS → TCP → TLS → HTTP`의 각 단계가 GitHub Pages라는 서비스 안에서 잘 이어질 뿐입니다.
