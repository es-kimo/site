# 왜 프론트엔드는 함수형 컴포넌트를 선택했을까

<AIAssisted />

백엔드 코드를 보면 인스턴스 기반 패턴이 자연스러운 순간이 많습니다. 서비스 객체가 의존성을 들고 요청을 처리하고, 커넥션 풀이 자원의 생애 주기를 관리합니다. 반면 프론트엔드, 특히 React 생태계에서는 함수형 컴포넌트가 사실상 표준입니다.

이 차이는 어디서 올까요? "함수형이 더 좋은 패러다임"이라서가 아닙니다. 각 분야가 마주한 문제의 성격이 다르기 때문입니다.

## UI는 상태의 함수다

프론트엔드 애플리케이션은 몇 가지 독특한 환경 조건을 가지고 있습니다.

첫째, **UI는 현재 상태를 바탕으로 계산되는 결과물**입니다. 사용자가 버튼을 누르면 상태가 바뀌고, 바뀐 상태에 맞게 화면 전체가 다시 결정됩니다. 컴포넌트는 오랜 시간 살아 있는 비즈니스 객체라기보다, 매번 호출되어 현재 상태의 스냅샷을 반환하는 계산 단위에 가깝습니다.

```jsx
function Greeting({ name }) {
  return <h1>안녕하세요, {name}님</h1>;
}
```

이 컴포넌트는 입력(`name`)을 받아 출력(JSX)을 만드는 함수입니다. 자기만의 지속적인 정체성을 가진 객체가 아닙니다.

둘째, **피드백 루프가 짧아야 합니다.** 프론트엔드 개발에서는 CSS를 1px 옮기거나, 텍스트를 바꾸거나, 조건부 렌더링을 추가할 때마다 결과를 즉시 눈으로 확인하고 싶습니다. 코드를 수정하고 브라우저에서 바로 결과를 보는 흐름이 개발 경험의 핵심입니다.

셋째, **컴포넌트의 수명이 짧습니다.** 라우트가 전환되거나, 조건부 렌더링에 의해 컴포넌트는 수시로 생성되고 제거됩니다. 한 번 생성되면 애플리케이션이 종료될 때까지 살아 있는 백엔드의 서비스 인스턴스와는 성격이 다릅니다.

이런 환경에서는 컴포넌트를 "상태를 받아 UI를 반환하는 함수"로 바라보는 모델이 자연스럽습니다. `UI = f(state)`라는 React의 핵심 철학이 바로 여기서 나왔습니다.

## 백엔드에서 인스턴스가 자연스러운 이유

반면 백엔드는 **지속성 있는 책임 단위**를 다루는 일이 많습니다.

```typescript
class ConnectionPool {
  private connections: Connection[] = [];

  constructor(private maxSize: number) {
    this.initialize();
  }

  acquire(): Connection { /* ... */ }
  release(conn: Connection): void { /* ... */ }
}
```

커넥션 풀, 세션 관리자, 메시지 큐 리스너 같은 개념들은 생성과 소멸 사이에 의미 있는 생애 주기를 가집니다. 자원을 획득하고, 일정 기간 보유하며, 적절한 시점에 해제합니다. 이런 동작은 "상태를 가진 인스턴스"로 표현할 때 가장 자연스럽습니다.

여기서 강조하고 싶은 건 우열이 아니라 **적합성**입니다. 각 도메인이 다루는 문제의 성격이 다르기 때문에, 어울리는 추상화도 달라질 뿐입니다.

## React: 클래스에서 함수로

React에도 원래 클래스형 컴포넌트가 있었습니다.

```jsx
class Counter extends React.Component {
  state = { count: 0 };

  render() {
    return (
      <button onClick={() => this.setState({ count: this.state.count + 1 })}>
        {this.state.count}
      </button>
    );
  }
}
```

같은 동작을 함수형으로 작성하면 이렇게 됩니다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}
```

단순히 코드가 짧아진 것이 핵심이 아닙니다. 두 코드는 컴포넌트를 바라보는 관점 자체가 다릅니다.

클래스형 컴포넌트는 인스턴스가 생성되면 `this`에 상태를 보유하고, 메서드를 통해 자신을 갱신합니다. **인스턴스의 정체성이 유지되는 동안** 상태와 동작이 함께 살아 있는 구조입니다.

함수형 컴포넌트는 매 렌더마다 호출되어, 현재 상태에 맞는 결과를 반환합니다. 상태는 함수 안이 아니라 **React 외부(Fiber 트리)에 저장**되며, 함수는 그 상태를 읽어와 UI를 계산할 뿐입니다.

앞서 정리한 프론트엔드의 요구 조건―상태 기반의 선언적 UI, 짧은 수명, 빠른 피드백―과 더 잘 맞는 쪽은 후자입니다. React 팀이 Hooks를 도입하며 함수형 컴포넌트를 중심으로 전환한 것은, 프론트엔드가 풀어야 하는 문제에 더 적합한 모델로 이동한 결과입니다.

그리고 이 구조적 차이가 가장 분명하게 드러나는 영역이 있습니다. 바로 **핫 리로딩**입니다.

## 핫 리로딩에서 드러나는 구조적 차이

핫 리로딩(Hot Reloading)은 코드를 수정하면 페이지를 새로고침하지 않고도 변경사항을 즉시 반영하는 기능입니다. 프론트엔드 개발자의 피드백 루프를 극적으로 단축시키는 이 기능은, 클래스형과 함수형에서 전혀 다른 난이도를 보여줍니다.

### 클래스형: 인스턴스와 구현의 결합

클래스형 컴포넌트에서 렌더 로직을 수정한다고 가정해 봅시다.

```jsx
class Profile extends React.Component {
  state = { editing: true, name: '홍길동' };

  render() {
    // ← 이 부분을 수정하고 싶다
    return <div>{this.state.name}</div>;
  }
}
```

이때 핫 리로딩이 해야 하는 일은 다음과 같습니다.

1. 기존 인스턴스의 `this.state`를 보존한다
2. 새 클래스의 메서드를 기존 인스턴스에 연결한다
3. 이미 실행된 `componentDidMount` 같은 lifecycle은 다시 호출하지 않는다
4. `this`에 바인딩된 이벤트 핸들러가 정상 동작하도록 보장한다

인스턴스의 **정체성**은 유지하면서 **구현**만 교체해야 합니다. 문제는 상태(`this.state`)와 로직(`render`, lifecycle 메서드)이 모두 하나의 `this` 위에 얹혀 있어서, 이 분리가 본질적으로 까다롭다는 점입니다. 실제로 React Hot Loader는 이 한계 때문에 불안정한 동작이 잦았습니다.

### 함수형: 상태와 로직의 분리

같은 상황을 함수형 컴포넌트에서 보면 구조가 다릅니다.

```jsx
function Profile() {
  const [editing, setEditing] = useState(true);
  const [name, setName] = useState('홍길동');

  // ← 이 부분을 수정하고 싶다
  return <div>{name}</div>;
}
```

함수형 컴포넌트의 상태는 `this`가 아니라 React 내부의 **Fiber 트리**에 저장됩니다. 코드가 변경되면 React의 Fast Refresh는 이렇게 동작합니다.

1. 새 함수 정의를 모듈에서 가져온다
2. Fiber에 저장된 hook 상태(`useState`의 값들)는 그대로 유지한다
3. 새 함수 본문으로 컴포넌트를 다시 호출한다

상태 저장소(Fiber)와 렌더 로직(함수 본문)이 **처음부터 분리되어 있기 때문에**, 함수만 교체하면 됩니다. 인스턴스의 프로토타입을 조작하거나, lifecycle 메서드의 재실행 여부를 판단하는 복잡한 작업이 필요 없습니다.

다만 이 방식에는 중요한 전제가 하나 있습니다. Fiber에 저장된 hook 상태는 **호출 순서로 매핑**되기 때문에, 코드 수정 전후로 훅의 순서와 개수가 동일해야 합니다.

```jsx
// 수정 전
function Profile() {
  const [editing, setEditing] = useState(true);   // 슬롯 #1
  const [name, setName] = useState('홍길동');       // 슬롯 #2
  return <div>{name}</div>;
}

// 수정 후 — useState 하나를 제거
function Profile() {
  const [name, setName] = useState('홍길동');       // 슬롯 #1 ← 기존 editing 값이 매핑됨
  return <div>{name}</div>;
}
```

훅이 추가되거나 제거되면 기존 Fiber의 hook 리스트와 새 함수의 호출 순서가 어긋납니다. Fast Refresh는 이런 경우를 감지하면 상태 보존을 포기하고 컴포넌트를 처음부터 다시 마운트합니다.

이 제약의 근원은 React가 훅을 이름이 아니라 호출 순서로 식별하는 설계에 있습니다. [이전 글](../Frontend/react-hooks-조건부-호출)에서 다룬 "훅을 조건부로 호출할 수 없는 이유"와 정확히 같은 원리입니다. 런타임에서 렌더마다 훅 순서가 같아야 하듯, 핫 리로딩에서도 코드 수정 전후로 훅 순서가 같아야 합니다. 함수형 컴포넌트가 핫 리로딩에 유리한 구조인 것은 맞지만, 그 이점은 이 규칙 위에서만 성립합니다.

이것이 React 팀이 Fast Refresh를 함수형 컴포넌트 기준으로 설계한 배경입니다. 실제로 Fast Refresh에서 클래스형 컴포넌트를 수정하면 상태가 보존되지 않고 컴포넌트가 완전히 다시 마운트됩니다. 이는 기술적 한계라기보다, 클래스형 모델의 구조적 특성에서 오는 필연적 결과입니다.

## state는 클로저가 아니라 Fiber에 있다

함수형 컴포넌트의 동작을 설명할 때, "state가 클로저에 저장된다"는 표현을 종종 만나게 됩니다. 직관을 잡는 데는 도움이 되지만, 엄밀하게는 정확하지 않습니다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    // 이 함수는 count의 "현재 렌더 시점 값"을 포착한다
    console.log(count);
    setCount(count + 1);
  };

  return <button onClick={handleClick}>{count}</button>;
}
```

`handleClick`이 `count`를 기억하는 것은 맞습니다. 하지만 이것은 클로저가 **해당 렌더 시점의 값을 포착**하는 것이지, state를 **영속적으로 저장**하는 것이 아닙니다.

state의 실제 저장소는 React Fiber 노드의 `memoizedState` 연결 리스트입니다. `useState`가 호출되면 React는 현재 Fiber의 hook 리스트에서 해당 슬롯을 찾아 저장된 값을 반환합니다. 컴포넌트 함수가 새로 호출되어도 상태가 유지되는 이유는 클로저 덕분이 아니라, **Fiber 트리가 렌더 사이에도 살아 있기 때문**입니다.

이 구분은 앞서 본 핫 리로딩과 직접 연결됩니다. 만약 상태가 정말로 클로저에 저장되어 있었다면, 함수를 교체하는 순간 새로운 클로저가 만들어지면서 이전 상태를 잃어버렸을 것입니다. 상태가 함수 바깥(Fiber)에 있기 때문에, 함수 본문만 교체해도 상태는 보존됩니다.

## 환경이 추상화를 고른다

기술 생태계의 변화는 종종 패러다임 논쟁처럼 보입니다. "함수형이 객체지향보다 우수하다", "선언형이 명령형보다 낫다" 같은 이분법이 그렇습니다.

하지만 실제로 살아남는 추상화는 더 "고급"인 쪽이 아니라, **그 환경의 문제를 더 잘 푸는 쪽**입니다. 프론트엔드에서 함수형 컴포넌트가 표준이 된 것은, UI가 상태의 함수라는 특성, 짧은 피드백 루프의 요구, 컴포넌트의 빈번한 생성과 소멸 같은 환경 조건이 함수 호출 모델과 구조적으로 잘 맞았기 때문입니다. 핫 리로딩은 그 적합성이 가장 선명하게 드러나는 사례 중 하나입니다.

반대로, 지속적 상태 관리와 자원의 수명 추적이 중요한 백엔드에서 인스턴스 기반 모델이 여전히 설득력을 가지는 것도 같은 이유입니다. 어느 쪽이 더 좋은지가 아니라, **어떤 환경에서 무엇을 더 쉽게 표현하고 유지하게 해주는가**가 중요합니다.
