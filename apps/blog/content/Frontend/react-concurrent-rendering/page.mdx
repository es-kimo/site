# React는 왜 렌더를 중단할 수 있어야 했을까

<TOC items={toc} />

React의 전통적인 렌더링 방식은 상태(`state`)가 변경되면 컴포넌트 트리를 동기적으로 순회하며 화면을 계산하는 모델이었습니다. 한번 렌더링이 시작되면 전체 컴포넌트 계산과 가상 DOM 비교가 끝날 때까지 메인 스레드를 계속 점유합니다.

컴포넌트 트리가 작을 때는 이러한 동기 렌더링도 큰 문제가 되지 않습니다. 하지만 복잡한 데이터와 거대한 UI를 렌더링하는 동안에는 사용자의 키보드 입력이나 마우스 클릭, 화면 애니메이션 같은 긴급한 작업들이 메인 스레드를 할당받지 못해 화면이 멈추거나 입력이 밀리는 현상이 발생합니다.

React 18에서 도입된 동시성 렌더링(Concurrent Rendering)은 이러한 병목을 해결하기 위해 렌더링 작업을 잘게 쪼개어 도중에 중단(Interrupt)하고, 우선순위가 높은 작업을 먼저 처리한 뒤 다시 재개(Resume)하거나 폐기할 수 있도록 설계된 아키텍처입니다.<Footnote id="1">1</Footnote>

## 동기 렌더링 모델의 한계: 메인 스레드 블로킹

브라우저의 자바스크립트는 단일 메인 스레드(Single Thread)에서 실행됩니다. 즉, 자바스크립트 연산, 사용자 입력 이벤트 처리, 브라우저의 레이아웃 계산 및 화면 그리기(Paint)가 모두 같은 스레드 위에서 순차적으로 처리됩니다.

```text
setState 호출 ──> [전체 컴포넌트 재귀 순회 및 가상 DOM 계산 (중단 불가)] ──> DOM 반영
```

만약 컴포넌트 트리를 렌더링하는 데 100ms가 걸린다면, 그 100ms 동안 브라우저는 사용자의 키보드 입력을 화면에 표시하지 못하고 멈추게 됩니다. 이를 입력 지연(Input Lag) 또는 프레임 드롭(Frame Drop)이라고 부릅니다.

아래 Playground에서 검색창에 글자를 빠르게 타이핑해 보면 입력 지연을 직접 체감할 수 있습니다.

<Playground

  previewHeight={200}
  code={`import { useState } from 'react';

    const filtered = items.filter(item => item.includes(query));
    return (
        <ul style={{ height: 120, overflow: "auto", fontSize: 13 }}>
            {filtered.slice(0, 50).map(item => <li key={item}>{item}</li>)}
            {filtered.length > 50 && <li>... 외 {filtered.length - 50}건</li>}
        </ul>
    );

    const [query, setQuery] = useState('');
    return (
        <div style={{ padding: 16 }}>
            <input
                value={query}
                onChange={e => setQuery(e.target.value)}
                placeholder="검색어를 빠르게 입력해보세요"

글자를 빠르게 입력할 때마다 키보드 입력이 뚝뚝 끊깁니다. 8,000개 아이템의 가상 DOM을 계산하는 무거운 렌더링 작업이 메인 스레드를 독점하여, 브라우저가 키보드 입력 이벤트를 즉각 화면에 반영하지 못하기 때문입니다.

## 협력적 스케줄링(Cooperative Scheduling)과 시분할

동시성 렌더링은 멀티스레드를 활용해 병렬로 연산하는 것이 아닙니다. 단일 스레드 환경에서 작업을 작은 단위로 쪼개어 브라우저에 제어권을 양보하며 시간을 나눠 쓰는 협력적 스케줄링(Time Slicing) 모델입니다.

React는 렌더링 작업을 수행하다가 주기적으로(약 5ms 단위) 스케줄러를 통해 브라우저에 처리해야 할 다른 긴급 작업(사용자 입력, 애니메이션 등)이 있는지 확인합니다.<Footnote id="2">2</Footnote>

이러한 협력적 스케줄링 덕분에 무거운 렌더링 작업이 진행 중이더라도 사용자의 인터랙션은 지연 없이 즉각 반응할 수 있습니다.

## 중단 가능한 Work Loop와 Fiber 구조

기존 자바스크립트의 일반적인 함수 호출 스택(Call Stack) 기반 재귀 구조로는 실행 중인 연산을 중간에 멈추거나 원하는 지점에서 재개할 수 없습니다.

React는 이를 해결하기 위해 호출 스택을 가상화한 Fiber 구조체를 도입했습니다. Fiber는 컴포넌트 트리를 부모(`return`), 첫 번째 자식(`child`), 다음 형제(`sibling`) 포인터로 연결한 연결 리스트(Linked List) 형태의 작업 단위입니다.

```js
// 단순화한 Fiber Work Loop
while (workInProgress !== null && !shouldYield()) {
  performUnitOfWork(workInProgress);
}
```

- `workInProgress`: 현재 처리 중인 Fiber 노드를 가리키는 포인터입니다. 작업 진행 상태가 메모리 객체에 보관되어 있으므로, 렌더링이 중단되더라도 이후에 정확히 멈춘 위치부터 작업을 재개할 수 있습니다.
- `shouldYield()`: 현재 할당된 실행 시간(약 5ms)을 초과했거나 브라우저에 처리해야 할 대기 이벤트가 있는지 확인하여 메인 스레드 제어권을 브라우저에 넘겨줍니다.

## 2단계 렌더링 파이프라인: Render와 Commit의 분리

렌더링 작업을 안전하게 중단하고 버리기 위해, React는 화면을 업데이트하는 과정을 Render 단계와 Commit 단계로 명확히 분리합니다.

<Mermaid chart={`
flowchart TD
    R["1. Render 단계 (가상 DOM 계산)<br/>- 컴포넌트 함수 호출 및 변경 사항 계산<br/>- 부작용이 없는 순수 연산<br/>- 중단(Interrupt), 재개(Resume), 폐기(Abort) 가능"]
    --> C["2. Commit 단계 (실제 DOM 반영)<br/>- 변경된 DOM 노드 삽입, 수정, 삭제<br/>- useLayoutEffect 및 useEffect 실행<br/>- 중간에 멈출 수 없는 원자적(Atomic) 동기 처리"]
`} />

| 단계 | 특성 | 중단 가능 여부 | 주요 작업 |
| :--- | :--- | :--- | :--- |
| **Render 단계** | 메모리 상에서 새로운 Fiber 트리를 구성하는 계산 과정 | 중단 가능 | 컴포넌트 함수 호출, JSX 평가, Diffing |
| **Commit 단계** | 계산된 변경 사항을 실제 브라우저 DOM에 적용하는 과정 | 중단 불가 (원자적) | 실제 DOM 조작, 레이아웃 계산, 이펙트 실행 |

Render 단계는 메모리 안에서 설계도를 그리는 작업에 비유할 수 있습니다. 계산 도중에 더 높은 우선순위의 새로운 상태 변경이 발생하면, React는 진행 중이던 미완성 트리를 폐기하고 최신 상태를 바탕으로 렌더링을 처음부터 다시 시작할 수 있습니다.

반면 Commit 단계는 실제 화면에 변경 사항을 반영하는 과정이므로 반드시 한 번에 원자적(Atomic)으로 완료되어야 합니다. 만약 Commit 단계가 도중에 중단된다면 사용자는 화면의 절반만 갱신된 불완전한 UI를 보게 되기 때문입니다.

## 우선순위 기반 렌더링과 startTransition

동시성 렌더링 엔진 위에서 개발자는 상태 업데이트의 우선순위를 선언적으로 지정할 수 있습니다. 대표적인 도구가 `startTransition`과 `useTransition`입니다.

React는 상태 업데이트를 크게 두 가지 범주로 분류합니다.

| 분류 | 업데이트 성격 | 예시 | 기본 처리 방식 |
| :--- | :--- | :--- | :--- |
| 긴급 업데이트 (Urgent) | 사용자의 직접적인 인터랙션에 대한 즉각적 피드백 | 글자 입력, 버튼 클릭, 드롭다운 선택 | 동기적으로 즉시 렌더링 |
| 전환 업데이트 (Transition) | 화면의 일부를 다른 뷰나 대량 데이터 결과로 전환 | 검색 결과 목록 필터링, 대시보드 탭 전환 | 중단 가능한 백그라운드 렌더링 |

아래 Playground는 검색어 입력(`setInput`)은 긴급 업데이트로 처리하고, 무거운 목록 필터링(`setQuery`)은 `startTransition`으로 감싸 전환 업데이트로 처리한 예시입니다.

<Playground
  editorHeight={360}
  previewHeight={200}
  code={`import { useState, startTransition } from 'react';

function HeavyList({ query }) {
    const items = Array.from({ length: 8000 }, (_, i) => \`아이템 #\${i + 1}\`);
    const filtered = items.filter(item => item.includes(query));
    return (
        <ul style={{ height: 120, overflow: "auto", fontSize: 13 }}>
            {filtered.slice(0, 50).map(item => <li key={item}>{item}</li>)}
            {filtered.length > 50 && <li>... 외 {filtered.length - 50}건</li>}
        </ul>
    );
}

export default function App() {
    const [input, setInput] = useState('');
    const [query, setQuery] = useState('');

    const handleChange = (e) => {
        const value = e.target.value;
        // 1. 긴급 업데이트: 사용자 입력은 즉시 화면에 반영
        setInput(value);

        // 2. 전환 업데이트: 무거운 리스트 필터링은 백그라운드에서 계산
        startTransition(() => {
            setQuery(value);
        });
    };

    return (
        <div style={{ padding: 16 }}>
            <input
                value={input}
                onChange={handleChange}
                placeholder="검색어를 빠르게 입력해보세요"
                style={{ width: "100%", padding: 8, fontSize: 14 }}
            />
            <HeavyList query={query} />
        </div>
    );
}`}
/>

`startTransition`을 적용하면 사용자가 글자를 빠르게 입력하는 동안 React가 기존 목록 필터링 작업을 일시 중단하거나 폐기하고 키보드 입력을 최우선으로 처리합니다. 입력이 잠시 멈추는 순간 백그라운드에서 필터링 렌더링을 완료하여 화면에 표시하므로, 입력 지연 없이 매끄러운 반응성을 유지할 수 있습니다.

## 동시성 렌더링 환경에서 지켜야 할 컴포넌트 작성 원칙

렌더링이 도중에 중단되거나 여러 번 다시 실행될 수 있는 환경에서는 기존 동기 렌더링 시절에는 드러나지 않던 잠재적 버그가 발생할 수 있습니다. 따라서 컴포넌트를 작성할 때 다음 원칙을 준수해야 합니다.

### 1. 컴포넌트 함수 본문은 순수 함수(Pure Function)여야 합니다

Render 단계는 언제든 중단되거나 폐기될 수 있습니다. 만약 컴포넌트 렌더 함수 내부에서 전역 변수를 수정하거나 네트워크 요청을 보내는 등의 사이드 이펙트(Side Effect)를 일으키면, 중단되거나 취소된 렌더링에서도 부작용이 남아 예측할 수 없는 버그로 이어집니다.

### 2. 모든 사이드 이펙트는 Commit 단계 이후(useEffect)에 수행해야 합니다

`useEffect`나 이벤트 핸들러는 실제 DOM 반영이 원자적으로 완결된 이후에만 실행되므로, 중단되거나 폐기된 렌더링의 영향을 받지 않고 안전하게 동작합니다.

### 3. React 외부 상태를 구독할 때는 useSyncExternalStore를 사용합니다

동시성 렌더링 도중 React 외부의 가변 상태(Window 속성, Redux 스토어 등)가 변경되면 동일한 렌더 주기 안에서 컴포넌트마다 서로 다른 상태 값을 읽어 화면이 불일치하는 티어링(Tearing) 현상이 발생할 수 있습니다. React 18의 `useSyncExternalStore`를 사용하면 이러한 외부 저장소의 동시성 불일치를 방지할 수 있습니다.<Footnote id="3">3</Footnote>
