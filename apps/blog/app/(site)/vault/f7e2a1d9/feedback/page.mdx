# Interview Feedback

읽어보니, 이 면접은 크게 두 파트였던 것 같습니다.

하나는 **과제 리뷰 기반의 설계/리팩터링 질문**, 다른 하나는 **실무 경험 기반의 직무 질문**입니다. 초반에는 퍼널 과제 구현을 두고 선택 근거, 상태 설계, useFunnel 사용 이유, URL/search param 필요성, score/answer/plan/index의 책임 분리, 가독성/리팩터링 포인트를 계속 파고들고 있고, 후반에는 ECG 그래프, 테스트 도입, 도메인 학습, CS 앱, 학습 방식, SSE 경험, 조직 문화 적합성 쪽으로 넘어갑니다.

결론부터 말하면, **답변 내용 자체는 나쁘지 않습니다.**
오히려 장점이 꽤 분명합니다. 다만 **말의 구조가 흔들리고, 질문의 핵심을 붙잡기 전에 사고 과정을 그대로 노출하는 순간들이 많아서**, 면접관 입장에서는 "생각은 있는데 정리된 답이 늦게 나온다"는 인상을 받았을 가능성이 큽니다. 특히 퍼널 과제 파트에서 그 경향이 강합니다. useFunnel을 고른 이유, 동적 질문에서 타입 추론 한계, search param의 장점, score는 퍼널 상태에 둘 필요가 없다는 판단 등은 좋은 재료인데, 답변이 정리된 주장보다 탐색 과정에 가깝게 들립니다.

## 유추되는 질문들

초반 과제 리뷰 파트에서 거의 확실한 질문은 다음 계열입니다.

- "과제 구조를 전체적으로 설명해 주세요."
- "왜 React Query를 썼나요?"
- "왜 useFunnel / muse-funnel을 썼나요?"
- "질문/결과 스텝을 그렇게 나눈 이유는?"
- "서브 질문을 배열 중간에 inject하는 방식은 왜 택했나요?"
- "이 설계의 문제점은 뭐라고 보나요?"
- "동적 API 질문에서 타입은 어떻게 다루려고 했나요?"
- "useFunnel이 없으면 어떻게 구현할 건가요?"
- "search param 기반 관리의 장점은 뭔가요?"
- "요구사항에 뒤로 가기가 없는데도 굳이 search param이 필요했나요?"
- "score / answer / plan / index 중 무엇이 퍼널 상태여야 하나요?"
- "이 코드에서 가독성을 해치는 부분은 뭔가요?"
- "어떻게 리팩터링하겠나요?"

후반 실무 경험 파트에서는 대략 이런 질문들로 보입니다.

- "최근에 했던 어려운 프로젝트를 설명해 주세요."
- "ECG 그래프 프로젝트에서 무엇이 어려웠나요?"
- "터치 이벤트 충돌은 어떻게 테스트하고 해결했나요?"
- "배포/스테이징에서 에러가 났던 경험이 있나요?"
- "E2E 테스트 도입 배경과 의사결정 과정은?"
- "E2E 테스트의 실제 효능은 있었나요?"
- "도메인 지식은 어떻게 학습했나요?"
- "비즈니스 로직을 이해한 경험을 말해 주세요."
- "평소 학습은 어떻게 하나요?"
- "실제로 어려웠던 기술 주제 하나를 예로 들어 주세요."
- "SSE를 왜 선택했고, 어떤 문제를 겪었나요?"
- "토스 조직 문화와 본인이 맞는 이유는?"

## 답변의 장점

좋았던 점부터 보면, 사용자는 **추상적 미사여구보다 실제 경험 기반으로 말하려는 경향**이 있습니다. 예를 들어 퍼널 라이브러리 선택도 예전 투표 시스템 경험과 연결해서 설명했고, 뒤로 가기/상태 정합성 문제를 언급했습니다. 또 muse-funnel의 타입 추론 장점과 동적 질문 구조에서의 한계도 인식하고 있었고, 런타임 validator 같은 대안을 떠올리기도 했습니다. 이것 자체는 "생각이 없는 지원자"의 답변이 아닙니다.

실무 경험 파트에서도 좋습니다. ECG 그래프 과제에서 다양한 터치 동작이 섞인 상태 제어 문제를 설명했고, 스토리북 기반 시나리오 테스트, Jira 문서화, E2E 도입 배경, 크리티컬 시나리오 중심 적용 같은 말은 모두 실무 감각이 있습니다. 특히 "QA 팀이 없어서 FE가 QA를 함께 떠안는 상황"과 "자잘한 수정 비용을 줄이기 위해 시나리오 범위를 제한했다"는 답변은 현실 감각이 좋습니다.

또 하나 좋은 점은, 완벽히 아는 척하지 않는다는 겁니다. "제가 못 찾았을 수도 있지만", "정확한 결론까지는 도달하지 못했다", "질문의 의도가 이게 맞는지 모르겠다" 같은 문장은 면접에서 무조건 나쁜 건 아닙니다. 모르면 모른다고 하는 태도 자체는 좋습니다. 문제는 그 표현이 **너무 자주, 너무 앞쪽에서 나와서** 답변 전체의 신뢰감을 깎는다는 데 있습니다.

## 가장 큰 문제 1: 결론이 늦다

가장 먼저 보이는 약점은 **핵심 주장보다 생각 과정이 먼저 나온다**는 점입니다.

예를 들면 과제 구조 설명에서, 사실 면접관이 듣고 싶은 건 이 정도였을 겁니다.

"질문 흐름은 퍼널로 관리하고, 질문 데이터는 API에서 가져오며, 제출 이후 결과 페이지는 React Query 캐시를 활용해 렌더링했습니다. 다만 질문/결과를 같은 퍼널 스텝으로 둔 점과 useEffect에 조작 로직이 몰린 점은 구조적으로 아쉬웠고, 리팩터링 시 퍼널 상태를 step/context 중심으로 재정의하려고 했습니다."

이렇게 먼저 말했으면 매우 좋아 보였을 텐데, 실제 답변은 중간중간 "잠시만요", "이게 맞을지는 모르겠습니다", "처음엔 이렇게 생각했고…"가 껴서 결론이 늦어집니다.

면접에서는 사고를 보여주는 것도 중요하지만, **정리된 판단을 먼저 주고 그다음에 근거를 붙이는 방식**이 훨씬 강합니다.

## 가장 큰 문제 2: 질문을 맞춰 들어가지 못하고, 생각 흐름에 끌려간다

과제 파트 중반부에서 이게 아주 잘 드러납니다. 면접관은 "뒤로 가기가 요구사항에 없는데 왜 search param 기반 설계를 했나", "score는 어디에 있어야 하나" 같은 식으로 설계 전제를 계속 좁혀 들어가는데, 사용자는 한동안 **'뒤로 가기가 있는 퍼널' 전제에 계속 머물러** 있습니다. 그러다 뒤늦게 "좀 전까지 계속 뒤로 가기가 있는 상태만 생각했다"고 스스로 말합니다. 이건 면접관 입장에서는 꽤 크게 보였을 수 있습니다.

즉 문제는 지식 부족만이 아닙니다.
**질문이 겨냥하는 논점을 빠르게 재설정하는 능력**이 부족해 보입니다.

이건 매우 중요합니다. 토스류 면접은 정답 암기보다 "상대의 문제 설정을 정확히 받아서, 그 틀 안에서 사고를 전개하는가"를 많이 봅니다.

## 가장 큰 문제 3: 본인 판단과 임시 추론이 섞여 있다

좋은 답변은 보통 아래 둘을 분리합니다.

- 내가 실제로 구현하며 내린 판단
- 지금 이 자리에서 새로 추론해보는 생각

그런데 지금 답변에서는 이 두 층이 자주 섞입니다.
예를 들어 타입 추론 얘기에서, 실제로 구현한 구조의 한계를 말하다가 "조드 같은 런타임 validator가 가능하지 않을까"로 넘어갑니다. search param 얘기에서도 "토스에서도 그걸 선택하신 게 아닐까"처럼 추정이 섞입니다. AI 활용 얘기도 마찬가지로, 질문과 직접 관련 없는 해명으로 흘러갑니다.

면접에서는 추론 자체가 나쁜 게 아닙니다. 다만 이렇게 말하는 편이 낫습니다.

"실제로 제가 구현하며 확신 있게 판단한 부분은 A입니다.
지금 즉석에서 더 생각해보면 B라는 대안도 가능해 보입니다. 다만 이건 당시 구현한 내용은 아닙니다."

이렇게 분리하면 훨씬 단단해 보입니다.

## 가장 큰 문제 4: 자기 약점을 먼저 크게 선언한다

몇 군데서 이런 표현이 눈에 띕니다.

- "퍼널 관리가 거의 처음이었다"
- "정확한 결론까지 도달하지 못했다"
- "모르는 부분일 수도 있다"
- "어디부터 봐야 될지 막막하다"
- "코드 문제점을 못 찾는데 해명이 되지는 않지만…"
- "바이브 코딩에 가까웠다"

이런 문장은 솔직해서 인간적으로는 좋지만, 면접에서는 위험합니다.
특히 **AI를 적극 활용했다**, **바이브 코딩에 가까웠다**는 말은 당시 시점의 토스 면접에서는 거의 득보다 실이 컸을 가능성이 높습니다. 면접관이 듣고 싶은 건 "AI를 써서 빨리 만들었다"가 아니라 "그 과정에서도 내가 어떤 기준으로 검증하고 구조를 판단했는가"입니다.

즉 약점을 말하려면 이렇게 바꿔야 합니다.

- 나쁜 방식: "바이브 코딩에 가까웠습니다."
- 좋은 방식: "초기 구현 속도를 높이기 위해 AI를 보조 도구로 썼지만, 후반 리팩터링과 상태 책임 분리를 충분히 못 한 점은 제 아쉬움입니다."

그러면 주도권이 다시 본인에게 옵니다.

## 가장 큰 문제 5: 본인 기여와 팀 기여의 경계가 약한 구간이 있다

후반 실무 경험 파트는 전반적으로 괜찮지만, E2E 테스트 도입 파트에서는 "팀장님이 오래 목표를 갖고 계셨다", "연차 있는 분이 시나리오를 제안했다", "리서치를 발표했다"가 섞이면서 **그래서 본인이 실제로 무엇을 ownership 했는지**가 조금 흐립니다.

이럴 때는 이렇게 정리되어야 합니다.

- 문제: QA 부재 + FE가 수동 검증 부담
- 내 역할: 라이브러리 리서치, 비교 문서 작성, 발표
- 팀 결정: 크리티컬 시나리오부터 제한 도입
- 결과: 아직 효능은 제한적이지만, 도입 경로와 운영 원칙을 세웠음

이렇게 ownership을 선명하게 보여줘야 합니다.

## 앞으로 더 생각해봐야 할 질문

이 면접 기록을 보면, 앞으로는 아래 질문들에 대해 **자기 언어로 한 번씩 정리**해두는 게 좋습니다.

첫째, 설계 질문입니다.
"상태는 어디까지 퍼널이 관리하고, 어디부터 외부 상태가 관리해야 하나?"
"동적 질문 + 타입 안정성을 함께 가져가려면 어디까지 정적 타입으로 하고, 어디부터 런타임 검증으로 넘길 것인가?"
"URL 상태가 정말 필요한 경우와 아닌 경우는 무엇인가?"
이 질문들에 대한 답이 정리되면, useFunnel/search param/컨텍스트/score 설계에 훨씬 강해집니다.

둘째, 리팩터링 질문입니다.
"가독성이 나쁜 코드란 정확히 무엇인가?"
"한 페이지에서 읽기 어려운 이유를 상태 책임, 부수효과 위치, 추상화 단위, 네이밍, 제어 흐름 측면에서 어떻게 설명할 것인가?"
지금 답변은 '읽기 어렵다'는 감각은 있지만, **왜 어려운지의 분해**가 약합니다. useEffect 안에 조작 로직이 몰려 있고, 히스토리 관리가 page 레벨과 섞여 있으며, 퍼널 조작 로직이 화면 렌더링 맥락을 침범한다고 식으로 더 구조적으로 말할 수 있어야 합니다.

셋째, 성과 질문입니다.
ECG 그래프와 E2E 테스트 도입은 좋은 사례인데, 결과가 조금 약하게 들립니다.
그래서 "충돌 케이스를 몇 개 정의했고, 어떤 류의 오류를 줄였는가", "문서화 덕분에 협업이 어떻게 쉬워졌는가", "테스트 도입으로 어떤 종류의 리스크를 미리 막을 수 있게 되었는가"를 더 구체화해야 합니다. 지금 기록에는 좋은 과정이 있지만 결과가 비교적 추상적입니다.

넷째, 회사 맞춤 질문입니다.
마지막 조직 문화 답변은 방향은 맞지만 조금 일반적입니다. "소규모 팀에 익숙해서 토스 문화와 맞을 것 같다"를 넘어서,
"작은 팀에서 FE가 제품 흐름 전체를 이해하고, 스스로 문제를 정의하고, 타 직군과 빠르게 맞춰야 하는 환경에서 내가 강점을 냈던 사례"로 연결돼야 훨씬 강합니다.

## 답변을 잘하기 위해 앞으로 어떻게 연습할까

가장 효과적인 방법은 **답변 템플릿을 강제로 적용**하는 겁니다.

모든 답변을 아래 4문장 구조로 먼저 말하는 연습을 하세요.

1. 결론
2. 이유
3. 구체 사례
4. 회고

예를 들면 퍼널 과제 질문이라면 이렇게요.

"핵심은 퍼널 상태의 책임을 너무 넓게 잡은 게 문제였습니다.
처음엔 질문과 결과를 같은 스텝 체계로 두고 배열 기반으로 제어했는데, 동적 질문과 중간 삽입이 섞이면서 useEffect에 조작 로직이 몰렸습니다.
리팩터링한다면 step/context만 퍼널이 갖고, score 같은 파생값은 외부 상태나 제출 시점 계산으로 분리하겠습니다.
당시엔 구현 속도를 우선했지만, 지금은 상태 책임 분리가 먼저였다고 봅니다."

이 정도 구조로 바로 말할 수 있어야 합니다.

그리고 사용자의 현재 말하기에서 특히 교정해야 할 습관은 세 가지입니다.

첫째, "잠시만요", "제가 잘못 이해했는데요", "질문 의도가 맞는지 모르겠습니다"를 너무 빨리 꺼내지 않는 것.
정말 필요할 때만 쓰세요.

"제 답은 A입니다. 이유는 B고, 제 코드에서는 C였습니다."
