# yjshd 성능 측정 기록

## 측정 환경

- **OS**: macOS
- **Node**: v22.18.0
- **Next.js**: 16.0.10
- **측정 일시**: 2026-01-27
- **측정 도구**: Lighthouse (headless Chrome)

## 라우팅 구조

```
app/
├── layout.tsx              # 루트 레이아웃
├── page.tsx                # / (홈)
├── (static)/
│   └── [category]/
│       ├── page.tsx        # /1.소개, /2.글모음, /3.강좌 (카테고리 목록)
│       └── [subCategory]/
│           ├── layout.tsx
│           ├── page.tsx    # /1.소개/1.의료진 소개 (MDX 콘텐츠)
│           └── [slug]/     # 동적 슬러그
└── (dynamic)/
    ├── 3.강좌/
    │   ├── 2.콩팥질환 정보/
    │   └── 3.혈액투석 1,2,3/
    └── 4.게시판/
        ├── layout.tsx
        └── page.tsx        # /4.게시판 (게시글 목록)
```

## 측정 대상 페이지

| 페이지       | URL                              | 특징                      |
| ------------ | -------------------------------- | ------------------------- |
| 홈           | `/`                              | 이미지, 스크롤 애니메이션 |

| 서브카테고리 | `/1.소개/1.의료진 소개`          | MDX 렌더링                |

## 측정 항목

- **TTFB**: Time to First Byte (서버 응답 시간)
- **FCP**: First Contentful Paint
- **LCP**: Largest Contentful Paint
- **TBT**: Total Blocking Time
- **CLS**: Cumulative Layout Shift

## 측정 방법

1. `pnpm build --filter=yjshd` 프로덕션 빌드
2. `npx next start` 프로덕션 서버 실행
3. Lighthouse CLI로 각 페이지 측정 (headless Chrome)

## After (최적화 후)

### 날짜: 2026-08-10

#### 측정 방법 변경 (중요)

위 Before(2026-01-27) 수치와 아래 수치는 **직접 비교하지 마세요.** 측정 조건이 다릅니다.

1월 측정에는 두 가지 문제가 있었습니다.

- **YouTube 임베드 오염**: `/1.소개/1.의료진 소개`에는 `<Video>` 임베드가 lazy 없이 들어있어,
  실행마다 iframe이 트레이스 창 안에 잡히는지 여부에 따라 전송량이 467KB ↔ 2037KB로 요동칩니다.
  Lighthouse의 `--blocked-url-patterns`는 크로스오리진 iframe(OOPIF)에 닿지 않아 차단도 불가능합니다.
- **단일 실행**: 회차 간 편차가 지표 변화량보다 큽니다.

그래서 이번 측정은 아래 조건으로 다시 잡았습니다.

- YouTube 임베드가 **없는** 페이지로 대상 교체 (`/1.소개/2.진료 안내`, `/2.글모음/3.새로운 장비 도입`)
- 페이지당 **3회 실행 후 중앙값**
- 서드파티 차단 플래그 적용

## 개선율 요약

| 지표          | Before | After  | 개선율      |
| ------------- | ------ | ------ | ----------- |
| Performance   | 97     | 97     | –           |
| TTFB (평균)   | 23ms   | 4ms    | **-83%**    |
| FCP (평균)    | 890ms  | 831ms  | **-7%**     |
| LCP (평균)    | 2653ms | 2551ms | **-4%**     |
| TBT (평균)    | 4ms    | 4ms    | –           |
| CLS (평균)    | 0.000  | 0.000  | –           |

**해석**: 가장 크게 움직인 것은 TTFB입니다. 특히 `/1.소개`가 76ms → 3ms로 떨어졌습니다.
정적화된 페이지는 이제 CDN 캐시가 가능하므로, 콜드스타트가 있는 실제 배포 환경에서는
로컬 측정치보다 훨씬 큰 차이가 납니다. FCP/LCP는 로컬에서 이미 병목이 아니어서 변화폭이 작습니다.

### 폰트: Noto Sans KR을 적용하지 않기로 한 이유

`fonts.css`가 404였다는 것은 **이 사이트가 한 번도 Noto Sans KR로 렌더링된 적이 없다**는 뜻입니다.
그래서 "죽은 요청만 제거"와 "실제로 웹폰트를 적용" 두 안을 각각 측정했습니다.

| 안                                 | Perf | TTFB | FCP    | LCP    | 전송  |
| ---------------------------------- | ---- | ---- | ------ | ------ | ----- |
| Baseline (죽은 폰트 404 상태)      | 97   | 23ms | 890ms  | 2653ms | 512KB |
| **A. 시스템 폰트 (채택)**          | 97   | 4ms  | 831ms  | 2551ms | 531KB |
| B. next/font `display: optional`   | 87   | 6ms  | 2412ms | 3588ms | 736KB |
| C. next/font `display: swap`       | 87   | 4ms  | 2411ms | 3587ms | 736KB |

B와 C가 사실상 동일한 이유는 병목이 swap 동작이 아니기 때문입니다. 실제 원인은 두 가지입니다.

- `next/font/google`의 Noto Sans KR은 `@font-face` **125개**짜리 CSS를 별도 파일로 뽑고,
  이게 **렌더 블로킹 스타일시트**로 추가됩니다 (+25.6KB, Lighthouse 기준 wasted 453ms)
- 한글 unicode-range 청크 9개(~150KB)를 **VeryHigh 우선순위로 FCP 이전에** 내려받습니다

`display`를 바꿔도 이 두 가지는 그대로라 FCP가 개선되지 않습니다.
Noto Sans KR을 다시 켜려면 `apps/yjshd/app/layout.tsx`에 `next/font/google`을 추가하면 되지만,
느린 4G 기준 FCP 약 +1.5초가 비용입니다.
